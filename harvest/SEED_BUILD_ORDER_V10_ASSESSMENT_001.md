# Seed Build Order V10 — Cross-Repository Assessment 001

## Status

This document assesses how the first engineering-logic and context-logic harvest affects `SEED_BUILD_ORDER_V10.md`.

It is not a replacement build order yet. It is the first formal amendment assessment.

## Executive conclusion

The original V10 build order is directionally correct but too linear and too kernel-centred for the knowledge already embedded across the Ventus repository federation.

The cross-repository guides reveal that V10 needs three additional foundations before deep implementation continues:

1. **authority and scope contracts**;
2. **grain, key and aggregation-law contracts**;
3. **audit, evidence and independent-verification infrastructure**.

The largest change is this:

> V10 should not merely build the engineering chain in the right physical order. It must also build the proof chain in parallel.

The revised programme therefore becomes two interlocked spines.

### Engineering spine

```text
objects
→ geometry
→ terminals
→ topology
→ properties
→ conditions
→ calculations
→ uncertainty
→ reports
→ visualisation
```

### Proof spine

```text
scope
→ provenance
→ declared grain and keys
→ invariants
→ audit
→ evidence receipt
→ independent verification
→ human authority decision
→ monitored state
```

Neither spine is complete without the other.

## 1. What remains valid in the current build order

The following existing decisions remain strong and should not be reversed:

- browser rebuild remains last;
- physical objects precede calculations;
- terminals and connectivity precede topology-dependent calculations;
- the Python engine remains the strongest provisional computation authority;
- V8 and V9 remain regression and lineage sources;
- the V10 JavaScript kernel remains a useful evidence and uncertainty source;
- standards cartridges remain separate from first-principles physics;
- reports are generated from canonical results rather than browser screenshots;
- cross-repository harvesting precedes final authority selection;
- copyright, confidentiality and licence boundaries remain non-negotiable.

## 2. What the original build order underestimates

### 2.1 Local guides are already part of the architecture

The repositories contain operating manuals, employer's requirements, data doctrines, audit rules, architecture notes, workflow guides, roadmaps and recovery plans.

These are not merely background reading. They contain executable design constraints.

Therefore repository-guide harvesting must occur before capability promotion, not as an optional documentation pass afterward.

### 2.2 Data laws and engineering laws need one framework

The original order recognises engineering objects and calculation tests but does not yet formalise:

- declared record grain;
- canonical keys;
- additivity or aggregation laws;
- legal unknown states;
- dependency-aware status propagation;
- current-state derivation from durable evidence.

These are necessary before the result schema and fleet aggregation can be authoritative.

### 2.3 Audit and apply must be separated

The original order includes testing and CI, but the wider repository doctrine adds another distinction:

- inspection and audit before mutation;
- apply only after review;
- post-apply receipt;
- live or clean-environment verification;
- rollback path.

This matters for schema migration, authority promotion, batch conversion and report changes, not only deployment.

### 2.4 Independent verification is not the same as unit testing

The federation guides insist that the builder not mark its own homework.

V10 therefore needs explicit independent verification stages:

- topology generator versus topology verifier;
- calculator versus known-answer or alternative implementation;
- writer versus schema/data-law verifier;
- local run versus clean-environment reproduction;
- technical candidate versus human authority approval.

### 2.5 Reports need a projection contract before rendered formats

The reports repository shows that report DNA and evidence objects should precede PDF, DOCX or polished HTML.

The original reporting phase should be split into:

- evidence object model;
- result schema;
- report projection manifest;
- baseline CSV/plain text/JSON;
- browser HTML review;
- optional formal rendered documents.

## 3. Revised V10 phase architecture

## Phase S0 — Seed federation receipt

Purpose:

Establish the complete repository and guide inventory before harvesting technical capabilities.

Deliverables:

- live repository receipt with default branch, visibility and head commit;
- canonical external-page links;
- document-class inventory;
- read-order map for every serious repository;
- upstream/fork/licence context;
- inaccessible and not-yet-observed states shown explicitly.

Exit criterion:

Every known repository has a receipt and every high-priority repository has a documented read order.

## Phase S1 — Scope and authority contracts

Purpose:

Define what Seed, the solar engine, reports, federation and browser layers are each allowed to own.

Deliverables:

- repository purpose contracts;
- permanent versus temporary classification;
- authority boundaries;
- approved scope and explicit exclusions;
- roles: owner, builder, verifier, approver, operator;
- migration decision vocabulary;
- authority-state vocabulary.

Exit criterion:

No capability can be promoted without a declared owner, scope and authority path.

## Phase S2 — Rights and provenance gate

Purpose:

Prevent accidental copyright, licence or confidentiality violations during harvesting.

Deliverables:

- rights receipt schema;
- licence and upstream fields;
- confidential abstraction protocol;
- standards-reference protocol;
- copy, adapt, reference and abstraction-only decisions.

Exit criterion:

Every harvested source has a rights classification before content or code migration.

## Phase S3 — Canonical grain, identity and aggregation laws

Purpose:

Define the engineering data spine before schemas proliferate.

Deliverables:

- engineering grain ladder;
- canonical identity rules;
- object, terminal, connection, segment, result, evidence and report keys;
- aggregation-law register;
- status and unknown-state vocabulary;
- temporal and physical grain rules.

Exit criterion:

Every planned result declares input grain, output grain, key and aggregation policy.

## Phase S4 — Repository and capability harvest

Purpose:

Recover the accumulated guides, mathematics, schemas, tests and lessons.

Deliverables:

- guide inventory;
- capability matrix;
- formula register;
- topology register;
- schema register;
- test register;
- report register;
- negative-knowledge register;
- lineage map;
- harvest receipts.

Exit criterion:

Every known computation capability has source path, context, rights status and migration decision.

## Phase V0 — Baseline execution receipts

Purpose:

Prove existing systems before consolidating or replacing them.

Deliverables:

- clean runs of Python tests;
- clean runs of V9 JavaScript tests;
- recoverable V8 baseline fixtures;
- V10 kernel baseline;
- deterministic exports and hashes;
- current failures recorded without weakening assertions;
- environment and command receipts.

Exit criterion:

Each existing computation family has a reproducible baseline and known failure register.

## Phase V1 — Canonical physical object model

Retain the original object-model work but add:

- canonical keys;
- event/change context;
- evidence references;
- rights-safe source metadata;
- status dimensions;
- declared grain.

Exit criterion:

A complete module-to-inverter circuit is represented without one assumed total length, and every object resolves to a stable key and evidence state.

## Phase V2 — Canonical topology and independent verifier

Split topology into two logical products:

1. topology generation;
2. topology verification.

Required proofs include:

- endpoints resolve;
- zero duplicate keys;
- no illegal polarity transitions;
- complete positive and negative traversal;
- branch and common-bus declarations are explicit;
- browser order cannot substitute for circuit order;
- invalid topology blocks dependent calculation.

Exit criterion:

Generated topology passes an independent invariant set over declared keys.

## Phase V3 — Authoritative steady-state kernel

Retain the original scope but add:

- formula identifiers;
- aggregation laws;
- result keys;
- independent known-answer verification;
- cross-language comparison receipts;
- legal unknown and provisional states;
- dependency-aware validity propagation.

Exit criterion:

One implementation is approved as authority for each steady-state capability, with a separate verifier and evidence receipt.

## Phase V4 — Route and installation physics

Retain the original scope but require every route result to state:

- spatial basis;
- dimensional basis;
- installation environment;
- completeness;
- included and excluded length components;
- aggregation law;
- evidence class.

Exit criterion:

Every conductor segment references a physical route segment and every route total can be decomposed and reaggregated reproducibly.

## Phase V5 — Distributed and transient models

Retain as a separate layer, with stronger entry conditions:

- steady-state authority stable;
- topology authority stable;
- geometry and formation schema stable;
- frequency-domain validity contracts defined;
- numerical-convergence receipts available.

Exit criterion:

Transient outputs are independently reproducible and cannot be confused with steady-state or standards-compliance results.

## Phase V6 — Standards and evidence cartridges

Retain the separation from physics and add:

- rights receipt for every standard source;
- source edition and jurisdiction context;
- interpretation author and reviewer;
- rule status: requirement, recommendation, example or unresolved;
- applicability conditions;
- exception and human-approval route;
- no copied protected wording, figures or tables.

Exit criterion:

Standards cartridges can be changed or disabled without changing the physical kernel and no compliance state is asserted without traceable applicability.

## Phase V7 — Evidence-aware result and event model

This phase should move earlier than polished reporting and become broader than the original result schema.

Deliverables:

- immutable calculation receipt;
- input snapshot hash;
- kernel version;
- result key;
- source object keys;
- formula and method identifier;
- units and conditions;
- assumptions and uncertainty;
- validation state;
- standards references;
- reviewer and approval state;
- supersession link;
- change event record.

Exit criterion:

No important number or state can appear without a complete authority and lineage chain.

## Phase V8 — Derived tables and database verification

Purpose:

Separate durable evidence and canonical objects from current-state and aggregate views.

Deliverables:

- deterministic DuckDB or equivalent builds;
- current-state views derived from canonical records;
- string, MPPT, inverter, site and fleet tables;
- exact key invariants;
- aggregation-law verification;
- orphan and dangling-reference checks;
- independent read-back verification.

Exit criterion:

All aggregates can be regenerated from lower-level canonical records and pass declared data laws.

## Phase V9 — Report DNA and baseline outputs

Purpose:

Define reports as projections rather than documents.

Build order:

1. report profile and DNA manifest;
2. evidence selection rules;
3. plain text output;
4. CSV output;
5. JSON machine output;
6. HTML review output;
7. optional PDF and DOCX renderers.

Exit criterion:

The same result set produces reproducible projections independent of browser state, and every displayed claim resolves to evidence.

## Phase V10 — Browser and external consumers

Only after stable contracts:

- browser edits candidate canonical objects;
- kernel validates and computes;
- browser renders verified results;
- browser save/export uses report contracts;
- Atlas, Spider, federation and other apps consume published interfaces;
- no consumer infers authority from visual state.

Exit criterion:

The browser can be replaced without changing engineering truth.

## Phase V11 — Controlled automation

Purpose:

Introduce automation only after audit contracts and permission boundaries exist.

Deliverables:

- audit mode;
- declared mutation target list;
- human approval gate;
- apply receipt;
- post-apply verification;
- rollback path;
- append-only operation events;
- threshold for cross-repository triggering and stronger authentication.

Exit criterion:

No automated mutation occurs silently or outside approved scope.

## 4. Immediate reordered execution queue

The previous queue should be amended to:

1. Complete live repository and guide receipts.
2. Classify document authority and repository read order.
3. Record rights, licence, upstream and confidentiality context.
4. Define canonical engineering grain ladder.
5. Define keys and aggregation laws.
6. Run existing computation families and preserve baseline receipts.
7. Complete capability, formula, topology, schema and test matrices.
8. Repair known tests without weakening valid assertions.
9. Define canonical physical object and evidence schemas.
10. Build topology generator and independent verifier separately.
11. Select steady-state authority capability by capability.
12. Add immutable calculation receipts and derived database views.
13. Build report DNA and baseline text/CSV/JSON outputs.
14. Add standards cartridges only after corresponding physics is authoritative.
15. Build transient models after steady-state, geometry and topology contracts stabilise.
16. Rebuild browser functions last.
17. Add controlled automation only after audit/apply and permission contracts exist.

## 5. Build-order gates

The repository harvest suggests that phases should not advance merely because files exist.

### Gate A — Scope gate

- approved scope exists;
- exclusions exist;
- authority owner exists;
- target list exists.

### Gate B — Rights gate

- source visibility known;
- licence or abstraction basis known;
- confidentiality status known;
- attribution obligations known.

### Gate C — Grain and key gate

- grain declared;
- keys declared;
- aggregation laws declared;
- unknown state supported.

### Gate D — Baseline gate

- existing implementation runs or failure is reproducibly recorded;
- environment recorded;
- outputs hashed;
- rollback reference retained.

### Gate E — Verification gate

- invariants run on declared keys;
- verifier is logically independent of builder;
- clean reproduction succeeds where required.

### Gate F — Authority gate

- competing implementations compared;
- evidence proportional to claim;
- human approval recorded;
- superseded implementation retained in lineage.

### Gate G — Publication gate

- report projection resolves to evidence;
- caveats and scope are present;
- confidential or protected content excluded;
- public route verified.

## 8. Risk assessment

### Risk: harvesting becomes documentation accumulation

Control:

Every harvest must identify affected capability, decision and build-order consequence.

### Risk: Seed becomes a monolith

Control:

Use stable identifiers and linked registers. Keep local operating brains in leaf repositories.

### Risk: public Seed leaks private or protected material

Control:

Rights gate before migration. Prefer original abstraction and source links.

### Risk: audit becomes bureaucracy

Control:

Use proportional gates. Exact identities and safety-critical claims receive stronger proof than low-risk presentation changes.

### Risk: independent verification doubles effort

Control:

Use different proof forms rather than duplicating code: invariants, hand calculations, read-back SQL, cross-language fixtures and clean-environment execution.

### Risk: browser delivery is delayed indefinitely

Control:

Allow thin prototypes against provisional contracts, but do not promote them to authority or hide calculations within them.

## 9. Final assessment

The surprise is real: the repositories already contain much of the Seed's missing constitutional and operational logic.

The work is not beginning from an empty knowledge base. It is beginning from a distributed body of doctrine that has been written in anticipation of a moment when it could be harvested, reconciled and made authoritative.

The original V10 plan was principally an engine recovery plan.

After this harvest, it should become an **engineering-and-proof operating-system build plan**.

That is the material change.

The engine remains central, but it no longer stands alone. Around it must exist declared scope, rights context, grain, identity, aggregation laws, evidence receipts, independent verification, report projection contracts and controlled mutation.

This does not slow the programme. It prevents V10 from becoming another powerful implementation whose authority and history later have to be reconstructed.
